# Essentials: encrypted actor-session-to-quotation challenge binding

**SOURCE ONLY. UNMOUNTED. ISOLATED PRIVATE STAGING D1 CANDIDATE. NOT CUSTOMER LOGIN OR CONSENT.**

This tranche of issue #2695 fills the server-held `loadSessionChallenge` dependency of existing #2697's consent POST/CSRF boundary and #2701's OIDC authorization-code PKCE handshake. The earlier #2696 one-time challenge store creates a 256-bit OIDC nonce and binds it to a frozen quotation, while #2704 creates a short-lived authenticated **tenant actor** session. Until now, neither persisted the sensitive nonce *as bound to a particular server session*. This candidate does that without browser storage.

## Trusted lifecycle

1. Only a separately authenticated, qualified **private server host** calls the existing #2696 `begin` to create a one-time quotation challenge and obtains its raw 256-bit nonce. The host then calls `bindSessionChallenge` with the independently authenticated actor session's opaque **SHA-256 cookie digest**, tenant-actor principal, quote ID and the newly created challenge object. The callback independently rereads the live session, current actor grant and frozen quote challenge from their own authority stores.
2. The binding computes SHA-256 of the *encoded nonce text*, encrypts the nonce with a **nonextractable AES-GCM 256-bit key**, fresh unique 96-bit IV and associated authenticated data covering session digest, tenant, actor, quotation, challenge ID, exact customer, nonce digest and issuance/expiry. Raw nonce is never placed in a D1 column or returned to a browser.
3. A single guarded `INSERT ... SELECT` in the SAME approved isolated D1 binds the exact active actor session to the pending one-time challenge and accepted frozen quote, checking tenant/actor/customer/quote version/amount/digest, exact nonce hash, issue time, both sessions' and challenge expiry using SQLite millisecond server time. The effective binding expiry is the earlier of the actor session and one-time challenge expiry. Duplicate and concurrent pending bindings fail closed.
4. The `loadSessionChallenge` callback rereads the **current actor session + independent current grant**, then the joined D1 binding, the unconsumed parent challenge and accepted frozen quote. The exact row is checked, the nonce is decrypted using the authenticated metadata and its hash recomputed, and the existing #2696 authoritative challenge reader rechecks nonce, actor, customer, quote and expiry. Only then does the trusted server receive the original nonce for the #2697 consent POST boundary or #2701 OIDC callback. Browser/client requests must NEVER obtain this nonce from a route or log.
5. A privileged private host may revoke the binding only after a separate `authorizeChallengeRevocation` callback. Its exact-row D1 UPDATE is one-way, with immutability triggers prohibiting deletion, rebinding, nonce modification or reversal. Revoking the parent actor session, changing the frozen quote or consuming/revoking the parent one-time challenge automatically denies future reads through the guarded join.

## Important remaining integration/transaction risk

The current source candidates use **two separate operations** — the original one-time challenge creation followed by encrypted session binding. If binding fails after challenge creation, an unbound pending challenge may remain until expiration and obstruct a retry. A qualified host must implement an independently reviewed, atomic *create-and-bind* transaction (or a separately authorized one-way orphan revocation/expiry recovery) and test retries/crashes before any real customer use. This PR **does not** claim that the multi-step begin journey is atomic, nor does it activate either step.

This actor session is *not the customer identity*. Actual customer OIDC authentication, independent ownership proof and verified account link, precise frozen quotation terms display and explicit acceptance are separate mandatory gates. No live IdP, customer endpoint, D1 schema, session cookie, private Worker or public route is provisioned. The encryption key and secure random source require independent host key custody/rotation and IV uniqueness controls; D1 must not contain or log the key.

## Offline tests and release approvals

Node tests use a real nonextractable AES-GCM key to check encrypted nonce binding, decryption, wrong session/actor/quote/customer, mutated ciphertext, revoked/expired parent, explicit one-way binding revocation and fail-closed database errors. SQLite tests execute the **actual exported JavaScript SQL** in-memory against all source-only candidate schemas to confirm accepted-quote and active-session/challenge joins, wrong hashes/identities, expiry, immutable nonce ciphertext, revocation and replay denial.

**No D1 execution, Cloudflare deployment, live website or production Finance operations authorized.** Protected source merge requires passing current-HEAD checks and a formal independent `thusico` approval. A separate exact-SQL, exact-resource owner authorization and independent reviewer approval, plus protected recovery and privacy/retention acceptance, are mandatory before isolated staging execution. Real customer production activation requires a distinct authorization.
