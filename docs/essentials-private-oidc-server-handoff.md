# Essentials private OIDC callback → explicit consent handoff (source only)

**UNMOUNTED. NOT REAL CUSTOMER AUTHENTICATION OR CONSENT. NO DB EXECUTION, CLOUD RESOURCE OR LIVE ROUTE.**

## Missing interface addressed

After the unmounted #2701 OIDC PKCE callback finishes, the confidential host receives an **UNVERIFIED** ID token; #2694 needs that same token when the customer later explicitly accepts the current frozen quote via same-origin CSRF-protected POST. Without a protected bridge, an implementation could be tempted to place the JWT in the browser, a URL, session cookie, logs or an unbound storage field. None is permitted.

This PR adds `server/essentials-private-oidc-server-handoff.mjs` and a **source-only, unexecuted** isolated D1 schema candidate. A host integrates it ONLY after independently verifying that `callbackResult` came directly from the previously approved and executed `pkce.complete()` for the exact current session. The host's injected `verifyTrustedOidcCompletion` MUST bind this invocation to the actual internal callback and cannot approve browser-supplied data.

## Process and controls

1. `recordOidcCallback({sessionKeyHash,callbackResult})` reads the **current, independently authenticated tenant-actor session** and the current encrypted quote challenge binding, requiring matching tenant, actor, quote, challenge, customer and valid expiry. It **does not trust or validate the JWT cryptographically**. It uses SHA-256 of a deterministic server-only session/challenge key as an opaque row locator.
2. The unverified ID token is encrypted under a nonextractable host-held AES-GCM-256 key with a fresh, unique 96-bit IV and authenticated metadata for locator, tenant actor, session, customer, quote, challenge and issue/expiry. An isolated D1 guarded INSERT checks the still-active session, binding, pending one-time challenge and frozen quote again at database time. Tokens are never returned to browsers or accepted from them.
3. The user must separately review the **actual frozen quotation and its full terms**, confirm the exact quotation digest, acceptance version and BWP amount, and perform a same-origin explicit acceptance POST. The host MUST first execute the separately reviewed #2697 origin, CSRF and cookie boundary and confirm the precise explicit-acceptance decision. Only then may its independent `authorizeExplicitConsentPost` callback return true.
4. `consumeForExplicitAcceptance` rereads the live session and bound challenge; a single guarded `UPDATE ... WHERE state='pending' RETURNING ...` permanently consumes the matching handoff. It rejects an expired, wrong-tenant, wrong-session, wrong-actor, wrong-quote, revoked/challenge-consumed or already-consumed handoff. AES-GCM decryption succeeds only with the original authenticated metadata. The service returns the JWT only **to the trusted server**, which must immediately pass it to #2694's pinned RS256 signature, issuer, audience, original nonce, fresh `auth_time`, customer-link and exact frozen-quote validators, followed by the existing atomic consent transaction.
5. If signature verification, account ownership or consent commit fails after token handoff consumption, this handoff cannot be replayed. The customer must reauthenticate with a new challenge. Never blindly retry a potentially committed acceptance.
6. New synthetic Node tests and an in-memory SQLite test execute the actual exported SQL for valid use, one-use replay, crossed session/tenant, revocation, ciphertext tampering, expiry constraints and malformed callbacks. The tests do not authenticate a real identity provider or prove an operational host exists.

## Critical blockers **before ANY staging activation**

- **Real customer identity/consent architecture:** The currently available session is for an authenticated *Thebe tenant actor*. It does not authenticate the outside customer. A real customer-facing session/invitation journey must be independently designed, approved and verified; a business employee acting on behalf of a customer does not itself constitute customer consent.
- **Real HTTPS host:** Trusted callback origin, provider code redemption, server-only result handling, session grant issuer, precise CSRF-protected POST, actual terms display and separate customer identity ownership verification are still unimplemented.
- **Encrypted ID-token retention:** The isolated D1 schema deliberately prevents unreviewed deletion and retains encrypted tokens even after consumption. A **separately reviewed short-retention/cryptographic-erasure procedure with durable replay tombstones and operator audit** is REQUIRED before real customer tokens can be stored. This is a **launch blocker**; source-only synthetic tests do not resolve it.
- **Secrets and operations:** Approve an actual IdP/client/issuer keys, separately provision encrypted key material and nonce IV uniqueness/rotation, isolate storage, validate staging backup/recovery and privacy, and run genuine negative E2E tests before requesting any route or customer activation.

**No staging D1 mutation, Worker upload, route, identity-provider setup, customer-facing acceptance or production Finance change is authorized.** Protected source merge needs exact-HEAD required CI and independent formal `thusico` review. Staging credentials/resources, SQL execution and recovery need separately scoped owner and independent reviewer approvals; production release is a distinct gate.
