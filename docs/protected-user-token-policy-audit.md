## Scope, restrictions and evidentiary limits

This review-only proposal adds a separate manually dispatched, protected, exact-current-main **read-only** job. It uses existing `production` environment review/protection and existing credential, never transfers or writes a secret. It verifies the user token via `GET /user/tokens/verify`, extracts the token metadata ID **in process memory only** and requests only that token's details with `GET /user/tokens/{token_id}`; no enumeration or fallback. It reports only coarse booleans (account-scoped allow, account-scoped `Write`/`Edit` permission names, and metadata completeness). Tokens, IDs, policy names, raw Cloudflare responses, and original errors are never logged or stored in repo or issues.

Cloudflare may deny detailed user-token metadata to the scoped user token itself. HTTP refusal is **HOLD**, not an instruction to enlarge its permissions or rotate it. `permission_groups` metadata may lack readable names; in that case `policyMetadataNamesComplete=false` and all least-privilege acceptance remains false. An account-wide allow for other non-write permissions still merits independent review. A true coarse write flag may show excessive account rights but does not establish endpoint-specific effective access; a false flag does not prove absence of elevated rights, because metadata may be incomplete and other credentials exist.

No token or secret creation/modification/revocation, no Cloudflare settings mutation, no database or R2 writes, no deployment, POP migration, payment or AI activation, restore approvals or isolated SQL imports. Any later protected manual run requires exact current main and explicit `AUDIT_USER_TOKEN_POLICY_READONLY` selection; reviewer approval of this PR does not authorize any restore or rotation.
