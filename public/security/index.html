Security & Trust

A public summary of security controls visible in the Thebe Desk implementation, together with the limits of what is currently independently assured.

Last updated: 14 October 2026
Assurance boundary. Thebe Desk does not currently claim SOC 2 or ISO 27001 certification on this page. Source-configured controls are not the same as an independent penetration test or certification.

1. Identity and access

  • Role-aware workspace access is used to separate owner, manager, reviewer, auditor and other authorised contexts.
  • Account passwords are required to meet a minimum length in the public server implementation.
  • Authentication endpoints use rate controls and production registration is designed to require anti-automation protection.
  • Social sign-in/linking paths include checks intended to prevent a linked identity being silently taken over by another account.

2. Web and application protections

  • Production configuration requires an HTTPS public origin.
  • Content Security Policy is configured, including restrictions on framing, objects and executable script sources.
  • Security headers are configured for HSTS, MIME sniffing protection, clickjacking protection, referrer controls and cross-origin isolation policies.
  • API responses are designed to avoid public caching of private API data.
  • Request-size, encoding, origin and rate protections are present in the public server implementation.

3. Evidence and file handling

  • Production startup is designed to fail when private object storage is not configured.
  • Production startup is designed to require malware scanning for uploaded evidence.
  • Evidence object integrity and file-signature checks are present in the server implementation.
  • Storage deletion is integrated with retention and account-deletion workflows.

4. Auditability and lifecycle controls

  • Important account, identity, evidence and deletion events are written to audit records.
  • Account export functionality is present.
  • Account deletion can be requested and can be blocked while a legal hold is active.
  • Session cleanup and explicit revocation/expiry handling are part of the server design.

5. Operational resilience

The public implementation includes request timeouts, graceful shutdown behaviour, structured request logging and health-oriented configuration checks. Backup frequency, recovery-point targets, recovery-time targets and hosting-region commitments are not yet published as contractual claims on this page.

6. Responsible security disclosure

If you believe you have found a security issue, do not attempt to access another customer's data or perform destructive testing. Use the public support channel and request a security escalation: WhatsApp +267 77 723 273.

Machine-readable disclosure guidance is available at /.well-known/security.txt.

8. Customer responsibility

Customers should use least-privilege roles, protect credentials, review high-impact AI output, keep legally required independent records where appropriate, and report suspected account compromise promptly.
